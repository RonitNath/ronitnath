isoastra core model · rn-site kernel · 2026-08-26

The kernel

One Rust binary is the application, the database, the message fabric and the realtime layer. It runs on three small VMs per zone, spread across sites far enough apart to survive a city-scale disaster, and is partitioned by region so writes are local and data stays where the law says. Products are plug-ins on this model.

Five rules

  1. Persons and organizations own; groups are granted. Ownership transfer is a command.
  2. Every change is a command; its audit row is in the same transaction; events come from commands.
  3. Read paths never write. Observations go on the async lane.
  4. A row lives in exactly one home zone. Moving it is a supported command.
  5. Budgets are gates, measured on the real cluster, before a rung ships.

People, organizations, groups

Party

Anything that can own, be granted, or belong. person — the human, global, one per human eventually. organization — a tenant and ownership boundary (a dental practice, isoastra itself). group — a set of parties; never owns, is granted: invitations, cohorts, audiences. service — a machine principal.

Identity

A registration, not a human. Source-scoped ("registered at rinity", "imported from AcquiredCo", "guest at event E"), holds the factors proven for that source, lives in one home zone, person_id NULL until resolved. Product data references the identity — never the person — so merging humans never rewrites product tables.

Merge is first class

Signals propose (same verified phone, same OIDC subject, same claimed link, name plus a shared group). Proof disposes: sign in to both, a shared verified factor, or an operator ruling with evidence. Never silent, always reversible — person_link is append-only and person_alias keeps old URLs alive. Merge is also recovery: from the merged person you can rotate the lost identity's factors.

One relation store

object #relation @subject answers every "may X do Y to Z": document:D #editor @person:P, group:X #member @link:T (an invitation), photo:F #viewer @group:X, person:P #contact @group:X, platform:* #operator @person:R. Leaking across groups would need a written row. Roles nest in code, not in SQL.

Principal

The one input to every check: Member { identity, acting_as: person | organization }, Bearer { link }, Anonymous. Expanded once per request into a subject set — the person, its groups, the org, authenticated, public.

Resource registry

Every ownable thing has a row: kind, public id, owner (person or organization), home zone, status; kind tables hang off it 1:1. Relations, links and audit FK here, so deletion cascades and "everything I can see" is one query.

Products plug in

A product registers resource kinds and a relation vocabulary (which relations a kind admits, which subjects each accepts — a patient record never accepts @public). It gets persons, organizations, groups, invitations, sharing, merge, sessions, placement and the fabric from the kernel.

Commands

Register · Merge · Split · Transfer · Share · Revoke · Disable · Migrate. One transaction each, audit row inside, typed event out. Status columns are projections of the commands that produced them; a status no command can produce does not exist.

check()

check(principal, relation, object) -> bool
  subjects = expand(principal)                        // once per request, cached per session digest
  rows     = SELECT relation FROM relation
             WHERE object = ? AND subject IN subjects  // one indexed query
  return any(row.relation ⊇ relation)                 // nesting in code: viewer<commenter<editor · member<admin<owner · hidden<busy<summary<full

Merge(absorbed → survivor), one transaction in the global group

  1. person_link rows for every identity of the absorbed person → survivor (method, evidence)
  2. memberships: union, strongest role wins
  3. relations with subject person:absorbed → person:survivor, union, strongest wins
  4. person_alias(absorbed → survivor); absorbed status merged; display fields kept on the link row
  5. audit and event person.merged; products apply step 3 to their own relation tables, idempotently

Split is the inverse with a fresh person. Sessions are untouched — they bind the identity. The older person survives. Invariants to test: product tables reference identity_id, never person_id; a merge on a weak signal alone is unrepresentable; groups never appear as owner_party_id; transfer is the only way an owner changes.

Storage & fabric

hiqlite, forked — multi-raft

Several raft groups in one process, each with its own membership: regional groups (SQLite state machines, voters across ≥3 sites in one zone), the global group (persons, groups, merges, routing; spread across regions; write-rare), and a log group per zone. Writes cost one intra-zone RTT plus one fsync; reads are local.

Zenoh, embedded

Notifications, cache invalidations, presence, CRDT update transport. Peers join and leave at runtime; geo-native; publisher caches let a reconnecting subscriber recover what it missed. Never a queue: nothing durable rides here. Later, the signalling plane for audio (str0m carries media).

The log group

The durable async lane and the change feed. Commands append typed events; the append returns immediately with a durable-offset watch; acks and reads wait for the offset they need (confirmed reads). Consumers hold cursors in the same state machine. Subscriptions read this log.

Two write lanes

Authoritative: anything an authz decision reads — synchronous, one transaction, audit inside. Observation: last_seen, telemetry, match scanning, mail, merge fan-out — asynchronous on the log, batched, idempotent, loss-tolerant by definition.

Loro CRDTs

Shared state across zones — documents edited from two regions, call rosters, presence. Each zone applies locally, appends the update to its own log, publishes it on Zenoh; the other zone imports it. Nobody waits on a foreign quorum. Never for invariants: money, uniqueness, capacity and permissions go through the object's home leader.

Not chosen

NATS stays for company products. Iggy is a server on compio with a static roster. SpacetimeDB is BSL (one production instance) with replication closed. io_uring stays outside the process until a flame graph asks for it.

Commitlog (per zone log group; clean-room, SpacetimeDB-shaped)

Placement

A group's voters sit on at least three sites of one zone: any one city can vanish and the zone keeps committing after one election timeout. The global group is the current nexus · nyc · delenda triangle, spread across regions and holding only what must cross borders. Residency is the voter and learner set — learners receive the full log, so an EU group with a learner in Virginia is a violation with a nice name; the group registry refuses out-of-region members, and snapshots, backups and keys stay in-region. Sharing across regions is a policy event recorded as a relation: it authorises a replica and revoking it deletes one. West-vs-east coast is the us region growing a second zone. Small countries get three domestic sites on separate providers; an encrypted out-of-region voter is admissible in principle and not built yet.

Quorum shapes: 3 voters on 3 sites (default, tolerates one site loss); 5 voters as 2-2-1 buys node slack, not disaster slack; a witness voter is not in openraft/hiqlite and relaxes raft's safety argument — do not build. Efficiency first: one binary per node (app, raft groups, Zenoh peer, log); a zone is three small VMs and a config file; learners are the read-scaling knob; SQLite until a zone's working set stops fitting a small node, with managed Postgres as the stopgap the plain-SQL discipline keeps open.

Surfaces

askama

Static, fast, no JS needed: the landing page, public pages, public event pages (the RSVP form posts a command and the page re-renders), auth forms, and the shell page that loads a bundle. Cached hard, no hydration.

Leptos CSR, one bundle per tier

/app member — what any signed-in person gets. /org operator — organization administration. /platform — the old /manage, platform operators only. The server picks the bundle from the principal's relations and serves an askama shell; a bundle you cannot hold is never sent. No role-routed /, no nav filtered by capability — the tier is the app.

Live data

The bundle subscribes; the server derives row diffs from the change feed and pushes them over one WebSocket; the bundle's store applies them and resumes by offset after a reconnect. Invalidate-and-refetch survives only as the resync after a release.

API shape

Commands: POST /api/cmd/<name>, JSON, idempotency key, returns the event offset. Queries: GET /api/q/<name>, cacheable, never write. Subscribe: WS /api/sub. whoami stays the only chrome DTO — public ids, display names, the relations the bundle needs, expiry; never emails or internal ids.

Harness, checked in and re-runnable: "no full scan" tests (every hot query under EXPLAIN QUERY PLAN asserting its index); oha load profiles with samply flame graphs on staging and latency_ms spans aggregated per operation; deterministic simulation (openraft turmoil) for the log group — partitions, clock skew, disk faults — landing with rung 8, not after; dated site-kill drills per zone; a lint that nothing reachable from a GET calls execute(). Physics: a global-group commit is one WAN RTT (60–120 ms) and that is fine because it is write-rare; a zone commit is one intra-zone RTT plus fsync; a naive io_uring swap is 1.06–1.10× and only an architecture built around the ring gets 2× — fsync is still a worker-thread op.

hiqlite patches, intended upstream, in order

  1. RaftType → a dynamic group registry: { name, sm_kind sqlite|cache|log, region, zone, members: voters/learners with site }
  2. Log state machine with cursors and a retention-aware snapshot policy (never snapshot away unread records)
  3. Group-scoped client: db.group("us-west").execute(…), db.log("us-west").append(…)
  4. Registry refuses out-of-region voters and learners; per-group backup target
  5. Network: separate heartbeat / append / snapshot channels (openraft #1170 head-of-line blocking)
  6. Later: quinn RaftNetworkV2 — 0-RTT never for appends; windows tuned for WAN

openraft facts to design around: election timeout ≫ RTT + max append; 3–5 voters, the rest learners; add_learner (blocking) then change_membership; per-follower AppendEntries is one-in-flight; a WAL is the right log store, RocksDB is not; failed formation state is poison — archive and start empty; a lone new voter never forms a quorum.
