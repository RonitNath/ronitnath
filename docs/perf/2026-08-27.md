# rn-site performance and resilience — 2026-08-27

Leg P1. Every number below was measured on this machine, on the revision named
here, by the checked-in harness. The raw evidence is in `docs/perf/2026-08-27/`
— one file per profile, oha's own table and JSON, the node logs, the flame
graph, the drill timelines — and this file is the reading of it, not a
substitute for it.

Nothing here proposes a fix. Where a budget fails, the failure is recorded and
the query or the frame responsible is named; the orchestrator routes the work.

Two conditions the harness enforces and records rather than asserts. Nothing is
measured while a `cargo`, `rustc` or `trunk` process is running, and every
profile writes down the one-minute load average it started at (4.1–5.8 across
the profiles below, 3.6 for the benches, 6.0 and 11.7 for the two drill rounds
— the drill's second round is the one number here taken on a busy machine).
The ceiling was raised from 4 to 6 for one reason worth stating: three idle
raft voters and this laptop's own background work sit near 4 on their own, so a
ceiling of 4 with the cluster up is a gate that never opens.

**`tools/cluster.sh` builds the dev profile, which is `opt-level = 0`.** The
budgets in the kernel report are microseconds of released code, so measuring
that binary against them would produce a table of failures about the compiler.
`tools/perf/run.sh` therefore raises the profile through
`CARGO_PROFILE_DEV_OPT_LEVEL=3` and turns debug assertions off, and says so in
`run.txt`. It does not edit `cluster.sh`, which this leg does not own — but a
cluster script whose binary is a debug build is a trap for the next person, and
it is on the findings list below.

## The three largest costs

Facts, not proposals.

**1. `member_documents::held` is quadratic in the principal's grants, and is
not bounded by the page.** `HELD_SQL` returns every relation row the
principal's subject set holds on any document — 10 004 rows for the seeded
owner — and `held()` folds them into a `Vec` with a linear
`best.iter_mut().find(…)` per row (`crates/server/src/api/query/member_documents.rs:141`).
That is ~50 million comparisons for a page of 200. `summary()` then does a
second linear `held.iter().find(…)` per listed row. The list itself is capped
at `PAGE = 200`; the grant read behind it is capped at nothing.

**2. SQLite page fetching, not statement planning.** `sqlite3_step` is 12.11%
of total samples with only 1.08% in `sqlite3VdbeExec`'s own body; the weight is
`getPageNormal` 6.31%, `getAndInitPage` 6.20% and `pcache1Fetch` 6.13% — pages
being pulled through the cache, which is what reading 10⁴ relation rows to
render 200 looks like from underneath. The kernel's own `list_visible` is
3.545 ms at the same 10⁴ (criterion, `benches/list.rs`), so the statement the
endpoint runs is not the statement the bench proves.

**3. The same read costs eight times more through three voters than through
one.** Identical mixed profile, identical seed size: 218.8 ms p50 on the
single node under samply against 1 408.7 ms p50 on the three-voter cluster;
writes 89.1 ms against 669.6 ms. Reads are local to the node that serves them,
so this is not replication latency in the read path — it is what the same host
running three hiqlite instances does to a query that was already expensive.

## The resilience drill

`tools/perf/drill.sh`, two rounds, 150 s of write load each, `--reads 2`. The
leader is killed first and the load is pointed at a node that is not it:
killing a follower proves nothing anybody doubted. `cluster.sh kill` sends
SIGTERM, and a node drains for about 9.5 s before it exits, so "one voter down"
means "one voter gone", not "one signal sent" — the timelines below start
counting from the process actually being gone.

| | round 1 | round 2 |
|---|---|---|
| leader killed | node 1 at t+25.0 | node 2 at t+25.0 |
| load and reads on | node 2 | node 1 |
| load average at start | 6.01 | 11.72 |
| **one voter down** — commits stall for | **6 s** (t+35 → t+40) | **6 s** (t+35 → t+40) |
| errors during that stall | 0 refusals, 0 transport errors | 0 refusals, 0 transport errors |
| second voter killed | node 3 at t+80.2 | node 3 at t+80.2 |
| **two voters down** — commits stall for | **24 s** (t+90 → t+113) | **27 s** (t+90 → t+116) |
| declines during the no-quorum window | **0** | **0** |
| slowest single write | **24 367.7 ms** | **27 595.8 ms** |
| reads on the survivor, no quorum | 20/20 `200`, 7.3–8.2 ms | 20/20 `200`, 7.2–8.8 ms |
| restart → three voters, all `/readyz` ok | **5.3 s**, 0 retries | **5.7 s**, 0 retries |
| a command commits after that | yes, within 2 s | yes, within 2 s |
| stale-revision declines on rejoin | 56 in one second (t+117) | 1 905 across the round |

Read across the two rounds:

* **Kill one voter → commits continue.** Confirmed twice, with the *leader*
  killed. Six seconds of stall, no errors of any kind in it, and the load
  resumes at its previous rate. Well inside the kernel report's "≈ one
  election timeout" for a site loss.
* **Kill two voters → writes refuse.** **Not confirmed — they hang.** In both
  rounds the no-quorum window contains zero declines and zero 500s, because it
  contains zero *answers*: every in-flight write blocked until quorum came
  back, 24.4 s in round 1 and 27.6 s in round 2. The server mounts no timeout
  layer (`crates/server/src/http.rs` has none), so "no hangs longer than the
  request timeout" is a claim about a timeout that does not exist. The reads
  half of the claim holds: the survivor answered all 20 probes with 200 in
  ~8 ms while it could not commit anything.
* **Restart → converges.** 5.3 s and 5.7 s from issuing the restart to three
  voters reporting `ok`, no retries needed, and a command commits immediately
  after. A rejoining node produces a burst of stale-revision declines while it
  catches up — see finding 2.

## Findings

Each of these was reproduced. None of them is fixed here; `tools/perf/**` and
`docs/perf/**` are this leg's only writable paths.

1. **`GET /api/q/documents` is 61× over its budget at one connection and 830×
   at eight** (306.6 ms and 4.15 s p99 against 5 ms). The cost is
   `member_documents::held` — quadratic in the principal's grant count and
   unbounded by the page — plus the SQLite paging that reading 10⁴ relation
   rows implies. `crates/server/src/api/query/member_documents.rs:141`. The
   kernel bench that covers "list visible" (3.5 ms) proves a different
   statement than the one the endpoint runs, so the gate as written did not
   catch this.

2. **A command's preconditions are read from the local state machine, so a
   node that has not applied the last entry declines a valid request.**
   `edit_document` loads the document and compares `draft_rev` before the raft
   write (`crates/kernel/src/cmd/edit_document.rs:76`). Reproducible without
   any node being down: `create-document` posted to a *follower* immediately
   after the `register` that created the person is declined every time, and
   one retry 50 ms later succeeds. Under sustained edit load the rate is 0.02%
   on the leader (8 of 33 902) and **20%** on a follower; on a rejoining node
   it spikes (1 905 in one drill round). Nothing is lost — the UPDATE carries
   its own `WHERE draft_rev = expected_rev` — so this is liveness and a
   confusing 403, not a correctness bug.

3. **With no quorum, a write hangs instead of declining.** 24–27 s observed,
   bounded only by when quorum returned. There is no request-timeout layer on
   the router. The plan's resilience row asks for "writes refuse with the
   uniform decline"; what happens is a hang.

4. **`POST /api/cmd/edit-document` is 47× over the commit budget at p99**
   (49.79 ms against ~1.05 ms) with a p50 of 4.51 ms and a max of 307.7 ms, on
   three loopback voters where the RTT is 0.053 ms. The budget is "one
   intra-zone RTT plus a millisecond"; nearly all of the measured time is
   neither.

5. **Fan-out to 100 subscribers is 18× over the notification budget** (p99
   18.4 ms against ~1.03 ms), of which the commit itself was 1.26 ms. Delivery
   is tight around its median (p50 17.70 ms, max 18.40 ms), which is the shape
   of a serial walk over subscribers rather than of a slow one.

6. **`tools/cluster.sh` builds and runs an unoptimized binary.** `cargo build
   -p rn-site` is the dev profile: `opt-level = 0`, debug assertions on. Every
   number in this report would have been the compiler's rather than the
   product's; `run.sh` raises the profile through the environment as a
   workaround. The script that is *named in the gate manifest* as the
   resilience harness should not need one.

7. **A restarted voter can fail to rejoin, and the process exits rather than
   retrying.** Seen twice during harness development, with two different words
   for one race: `ClientWriteError: has to forward request to: None, None` and
   `no such table: _migrations`. `db::migrations::apply` writes
   `CREATE TABLE IF NOT EXISTS _migrations` through raft and then reads it
   back locally, so a node still catching up asks about a table its own state
   machine has not seen (`crates/server/src/db/migrations.rs:87`). Both times
   the next start succeeded, and neither drill round reproduced it — but a
   node that exits on boot needs a supervisor to come back, and `cluster.sh`
   is not one.

8. **An idle keep-alive connection to the server is closed at around 13 s**
   with no `Connection: close` on the preceding response, so a client that
   pauses gets an empty read where a status line should be. Worked around in
   the harness's HTTP client; noted because a browser tab that idles will meet
   the same thing.
