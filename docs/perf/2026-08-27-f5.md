# rn-site performance and resilience — 2026-08-27, leg F5

P1 measured and named eight findings (`docs/perf/2026-08-27.md`). This leg
answers them, and every row below was measured twice on this machine by the
same harness: once on the revision P1's findings describe, once on the revision
that answers them. The raw evidence is in `docs/perf/2026-08-27-f5-before/` and
`docs/perf/2026-08-27-f5/` — one file per profile, oha's own tables and JSON,
the node logs, the flame graphs, the drill timelines, the phase decomposition.

One thing changed underneath both columns and it belongs first.
**`tools/cluster.sh` builds `--release` now** (finding 6). P1's numbers are the
dev profile at `opt-level = 3` with debug assertions off, raised through the
environment by `run.sh`; both columns here are the binary that ships. So
"before" is not P1's table — it is P1's *code* on this leg's build, measured
fresh. Where the two differ the difference is the compiler, and the largest of
those is worth stating up front: the commit profile P1 reported at 49.79 ms p99
is **4.755 ms** p99 on a release build. Finding 4 was mostly the debug binary.

## Finding 1 — the document list

**306 ms → 2.15 ms at one connection; 4.35 s → 12.8 ms at eight.** Within the
5 ms budget alone, ×2.6 over it saturated.

P1 named `member_documents::held` and it was not the cost. Fixing `held` alone
— one query bounded by the page, a `HashMap` instead of two linear scans —
moved the endpoint from 306 ms to 238 ms. The other 236 ms were two things
neither of which the flame graph's self-time ranking could show, because both
are SQLite doing the wrong amount of work rather than Rust doing any:

* **The planner drove the query from `party`.** `JOIN party owner ON owner.id =
  res.owner_party_id`, for two display columns, made `party` the *outermost*
  loop: the whole visibility question, once per party in the deployment.
  Written as two scalar subqueries on the primary key — which cannot be
  anything but a seek — that alone is 294 ms → 21 ms on the seeded world.
* **The candidate set was linear in everything the principal can see.**
  `res.id IN (` every visible id `)` builds 10 004 ids into a temporary b-tree
  and sorts them to return 200. Both branches are bounded now: ownership takes
  the newest page and stops, reading the ordering columns off
  `resource_owner_created_idx` (migration 5), and the grant branch drops
  `relation = 'owner'`, which is not a share and is exactly the set the first
  branch already has — a person who owns 10⁴ documents held 10⁴ owner grants,
  and the candidate set was all of them. 21 ms → 1-2 ms warm.

The bounding is sound rather than approximate: a row that is in the newest N
visible and is owned is necessarily in the newest N owned, and the page cursor
applies on both sides.

`relation::LIST_VISIBLE_SQL` got the same shape, so the bench named in the gate
manifest proves the statement the endpoint runs rather than a cousin of it —
which is what P1 meant by "the gate as written did not catch this". It is
faster for every principal the bench measures: owner first page 3.545 → 1.014
ms, second page 3.207 → 0.928 ms, reader 0.556 → 0.771 ms. The reader is the
one that got slower, by 0.2 ms, and that is the grant branch now doing a
`relation <> 'owner'` test it did not do before.

The EXPLAIN gate is stronger than it was: the plan must bind `object_id` in the
`held` seek (that is what "bounded by the page" means in a query plan) and must
reach `resource_owner_created_idx`. A shape that was measured and rejected is
recorded in the statement's own comment: driving the outer loop off
`resource_kind_created_idx` and filtering each candidate with `EXISTS` is 3 ms
for the owner and **21 ms** for a reader who can see 1 document of 10 009,
because that reader walks the whole kind looking for rows that are theirs. It
would have bought this leg's headline number by making the fan-out worse.

What is still unbounded is how much has been *shared* with one principal, since
`relation` carries no `created_at` to page on. That is a cost in what somebody
has been given rather than in the size of the deployment, and closing it needs
an ordering column on `relation`.

**One trap found on the way, and it is the kind that does not announce itself.**
SQLite reads `$1` as a *named* parameter, not a numbered one, and assigns names
their index in order of first appearance. A statement whose placeholders are
not written in ascending order binds its values to the wrong slots and silently
answers about nothing — the rewritten statement's first draft returned an empty
list for a document the caller owned, and the EXPLAIN test passed the whole
time, because a plan is about shape and this was about values. Both statements
now name the order they bind in, and both call sites bind through one function.

## Finding 2 — a follower declining a valid request

**Before: 11 of 41 `create-document`s declined and 9 of 50 `register`s, posted
across two nodes with nothing in between. After: 0 of 50, twice.**
`tools/perf/crossnode.py` is the measurement, and it works on either build: it
reads the offset the register landed at out of `x-rn-offset` and sends it back
as `x-rn-after`, which a build that honours it waits on and a build that does
not ignores.

Under sustained load on a follower the drill is the sharper number: **4 908
declines in 39 763 writes (12.3%)** before, **150 in 52 301 and 149 in 52 508
(0.29%)** after — and every one of them is in the three seconds after quorum
came back, which is a different thing (see finding 3).

### The choice: read-your-writes, not consistent reads

Option (a) was to route command preconditions through hiqlite's
`query_consistent`, which runs on the leader behind a linearizable read
barrier. It needs no client cooperation at all, and that is its whole appeal.
It also puts a leader round trip and a raft read barrier in front of *each* of
the four or five reads a command makes — on a path whose measured raft
transaction is already 1.38 ms against a 1.05 ms budget — to buy global
linearizability for a problem that is per-caller staleness.

Option (b) is what the kernel report already specifies for the log group:
*acks and reads wait for the offset they need*. A command reply carries the
offset its event landed at; the caller sends it back as `CommandEnvelope.after`;
the node waits until its own feed head has reached it before reading anything.
The waiting side is one local `max(id)` read, taken only when the caller
presents an offset and skipped outright when this node is already past it —
which is the usual case. That is (b), and it is implemented.

Three details worth stating:

* **The wait happens before the session is resolved.** The session `register`
  minted is one of the rows a stale node has not applied, so a barrier that ran
  after authentication would answer 403 to a cookie it was about to be able to
  read. The `/api/cmd` route resolves the cookie itself, after the barrier,
  rather than through an extractor that would run before it.
* **Form posts have no envelope**, so every command reply also stamps
  `x-rn-offset` — including the `/auth` redirects, which have no body to say it
  in — and `x-rn-after` is accepted as the same thing. That is what lets a
  caller register on one node and immediately command another.
* **The bundle threads it** through `ui::api::command`, and also learns offsets
  from the diffs its subscription has already rendered.

### And the half that was not the precondition read at all

P1 attributed the declines to the precondition read. With the barrier in and
declines still at 23 of 43, the node logs said what was actually happening:

```
ERROR "kernel invariant violated" invariant="committed batch left no audit row"
```

`cmd::run` commits through raft, the call returns because a quorum has the
entry, and then it reads the audit row back from *its own* state machine, which
has not applied it yet. An invariant failure, reported for a command that
worked perfectly, and rendered to the caller as the uniform decline. It waits
for the row now — two seconds, at 200 µs a look. The row is not in doubt: the
batch committed and the audit statement is inside it under the same guard. Only
when this node catches up is, and a node that never does still gets the
invariant failure it deserves.

That fix is what took the count to zero. Both halves were needed: the barrier
for the cookie and the person, the read-back wait for the command's own event.

## Finding 3 — no quorum

**Before: the slowest write took 27 578 ms and answered nothing until quorum
came back. After: 5 002.9 ms, and a `503`.**

| | before (1 round) | after (2 rounds) |
|---|---|---|
| one voter down (the leader killed) | commits stall 6 s, 0 errors | stall 6 s and 5 s, 0 errors |
| two voters down — what a write does | **hangs**; 0 declines, 0 answers | **503**, 47 and 48 of them |
| slowest single write | **27 577.3 ms** | **5 002.9 ms** and 5 002.1 ms |
| reads on the survivor, no quorum | 20/20 `200`, 1.9-2.6 ms | 20/20 `200`, 1.9-4.0 ms |
| restart → three voters `ok` | **94.1 s**, 1 retry | **4.2 s** and **5.4 s**, 0 retries |
| a command commits after that | yes, 2.0 s | yes, 2.1 s and 2.0 s |

The layer is written out in `crate::http` rather than mounted from
`tower_http::timeout`, and the reason is the shape of the answer. That layer
sends `408 Request Timeout` with an empty body; `408` says the *client* was
slow, and what this refuses is a cluster that cannot commit. `503` with the
uniform decline body is the honest pair. Five seconds for a write, two for a
read, `/api/sub` excluded because a deadline on a subscription is a deadline on
the tab, and assets and documents left off the clock because a large file over
a slow link is a long response and not a stuck one.

A timed-out command is **undecided, not undone**: the handler's future is
dropped, which cancels this node's wait, and a raft entry already in flight may
still apply. That is what the idempotency key is for, and `503` is the status
that says "unknown" — which is also where the drill's remaining 403s come from.
They arrive in the three seconds after quorum returns, when a worker whose
write timed out retries against an `expected_rev` that its own timed-out write
has since moved. The load generator re-reads and carries on. That is the
contract working, not a fault.

hiqlite 0.14 exposes no client-side write timeout — `NodeConfig` carries rate
limits and raft timings and nothing that bounds one call — so this layer is the
bound.

## Findings 4 and 5 — where the commit and the fan-out go

`cmd::run` now records its own phases under `RUST_LOG=rn_kernel::cmd=debug` —
free when it is off — and `tools/perf/phases.py` turns a node log full of them
into percentiles. On the leader, writes only, 20 s, a 200-document world
(`docs/perf/2026-08-27-f5/phases.txt`):

| phase | p50 before | p50 after | p99 before | p99 after | what it is |
|---|---|---|---|---|---|
| replay | 0.056 ms | 0.055 ms | 0.306 ms | 0.356 ms | the idempotency-key read |
| plan | 0.001 ms | 0.001 ms | 0.014 ms | 0.015 ms | the preconditions |
| commit | 1.129 ms | 1.377 ms | 2.293 ms | 2.503 ms | the raft transaction |
| read back | 0.135 ms | 0.170 ms | 0.477 ms | 0.580 ms | the audit row |
| notify | **0.780 ms** | **0.001 ms** | 1.485 ms | 0.029 ms | telling the other nodes |
| **total** | **2.125 ms** | **1.645 ms** | 3.845 ms | 3.020 ms | 2 988 → 3 586 writes/s |

**It is not the guarded-batch retry and it is not cache eviction.** Planning is
one microsecond, so a second plan would be invisible; the retry does not fire.
The two things that are ours are the second-largest term and it is now gone:
`Feed::notify` is a *second* raft write — hiqlite's notify goes through the
cache group — and it was sitting between a command committing and its caller
being told. It is spawned now. Nothing durable rides on a wake-up: the offsets
are hints, every subscriber reads the audit table from its own cursor, and this
node's own sockets are woken in-process before the spawn.

**What is left is the raft transaction, 1.377 ms at p50, against a budget of
one intra-zone RTT plus a millisecond — where the RTT here is 0.056 ms.** That
is quorum plus a WAL append on one laptop disk running three voters, and it is
not ours. The budget row's measured note moves; the budget does not.

### The fan-out is a read path, not a walk

P1 read the tight distribution as "a serial walk over subscribers". It is not a
walk at all — every socket is its own axum task with its own broadcast
receiver, and always was. Waking them locally instead of through the cache raft
group did take the commit's own reply from 3.193 ms to 1.440 ms, and the
one-subscriber case is 2.7 ms. But delivery at 100 subscribers is 34.7 ms in
the run above and 41.4 ms in the scaling sweep — the sweep is a second seeding
of the same world, and the spread between the two is this machine — and
`fanout-scaling.txt` says where it goes:

```
  1 subscriber    2.7 ms        25 subscribers   14.1 ms
  5 subscribers   3.5 ms        50 subscribers   22.6 ms
 10 subscribers   6.6 ms       100 subscribers   41.4 ms
```

0.4 ms per subscriber, close to linear, and every socket's diff arriving inside
a 1 ms window at the end — the signature of a hundred concurrent readers
contending, not of a queue being drained one at a time. Two things it is not:
it is not the load generator (`RN_PERF_WORKERS=8` instead of 2 moves it from
41.4 ms to 37.6 ms) and it is not the read pool (raising hiqlite's
`read_pool_size` from its default 4 to the core count moved it by nothing).

What it is, is that **the local read path does not scale with concurrency**
(`read-concurrency.txt`). The same `GET /api/q/documents`, as a subscriber who
can see one document:

```
 1 connection   3 687 req/s   p50 0.24 ms
 2 connections  5 072 req/s   p50 0.36 ms
 4 connections  3 845 req/s   p50 1.05 ms
 8 connections  3 046 req/s   p50 2.64 ms
16 connections  3 338 req/s   p50 4.64 ms
```

Throughput peaks at two connections and falls; latency is linear in
concurrency. A commit that touches 100 sockets is 200 reads — one feed read and
one query re-read each — and at roughly 3 500 serialized reads a second that is
55 ms of work no matter how many cores are idle. That is the fan-out number,
and it is inside hiqlite's `query_owned_local` rather than in anything this leg
owns. It is the next thing to look at, and it is a bigger prize than the fan-out
alone: it is the ceiling on every read the deployment does.

## Finding 7 — a restarted voter that did not rejoin

Reproduced on the "before" build on the first attempt: the drill's restart took
**94.1 s and needed a retry**, because a node exited on boot rather than
waiting. `db::migrations::apply` wrote `CREATE TABLE IF NOT EXISTS _migrations`
through raft and read it back *locally*, so a node still catching up asked
about a table its own state machine had not seen.

The read back goes through the leader now — `query_consistent_map`, the same
consistency path the write took, so the two cannot disagree — and the whole
apply is retried for thirty seconds against the two errors that mean "the
cluster has not settled" (a write forwarded to a leader mid-election, a table
this node has not applied) rather than "the schema has drifted". An
unrecognised error is still fatal: treating it as transient would turn a real
schema refusal into a thirty-second hang followed by the same refusal.

After: **4.2 s and 5.4 s, zero retries**, across two rounds.

## Finding 8 — the keep-alive close at ~13 s

**Not reproduced, and here is the measurement.** An idle keep-alive connection
to a voter on the release build is still open after **120 s** — with the
cluster idle, with a 30-second commit profile running on other connections, and
on a connection that had itself just run a `GET` and a `POST`
(`docs/perf/2026-08-27-f5/keepalive.txt`). axum's `serve` sets no idle timeout
and hyper has none by default, which agrees with the measurement.

What this server does do is close live connections without a `Connection:
close` on the preceding response, in exactly one place: the graceful shutdown
drain. `cluster.sh kill` sends SIGTERM and a node drains for about 9.5 s before
it exits — and the harness's profiles run either side of `cluster.sh`
start/kill. A client holding a socket across that sees precisely what P1
described: an empty read where a status line should be. That is the mechanism
this build has; whether it is the one P1 met on a debug binary cannot be
settled from here, so the harness keeps its one reconnect, which is what a
client library would do anyway.
